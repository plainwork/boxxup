quick start

The installer puts boxx in /usr/local/bin. On Linux it also installs Docker if it's missing, enables it at boot and adds you to the docker group.

$ curl https://get.boxxup.com | sh
$ boxx install <image> --host <hostname>  # deploy your first app
$ boxx  # open the TUI
$ boxx upgrade  # upgrade boxx to the latest release

the contract

An image works with boxx if it is a Docker image (public or private registry), listens for HTTP on port 80 and exposes GET /up returning 2xx. Anything written under /storage persists. When a database is requested, the app reads its connection from DATABASE_URL.

hostnames

Every app has one primary hostname and any number of extra ones. Point each hostname's DNS at the server first. A hostname can belong to only one app.

$ boxx host ls <app>
$ boxx host add <app> www.example.com --redirect
$ boxx host add <app> '*.example.com'  # one label, cert on first visit
$ boxx host primary <app> www.example.com
$ boxx host rm <app> app.example.net

groups: routing by path

A group puts several apps behind one hostname, each answering its own path prefix: the site at / and a separate admin app at /admin, say. The longest prefix wins, so /admin is matched before /. boxx strips the prefix before proxying, so the admin app sees / and serves its own GET /up, and sets BASE_PATH=/admin so it can build its links. With --db the group gets one database and every app reads the same DATABASE_URL, including apps added later. Each app keeps its own /storage volume. group add puts more apps in an installed group; it refuses a path or slug the group already has and leaves the running apps alone. The group's slug comes from its hostname (example.com becomes example-com), an app's from its path, or from its image for /. Hostname commands take the group slug; deploy, logs and remove take group/app.

$ boxx install-group --host example.com --db postgres \
    --app ghcr.io/acme/site:latest=/ \
    --app ghcr.io/acme/admin:latest=/admin
$ boxx group add example-com --app ghcr.io/acme/docs:latest=/docs
$ boxx deploy example-com/admin --image ghcr.io/acme/admin:v2
$ boxx env push example-com --app admin
$ boxx remove example-com/admin  # one app; the shared database stays
$ boxx remove example-com  # every app, the database and volumes

env

env push opens your $EDITOR on the app's variables, saves them and redeploys. boxx keeps the previous set, so you can roll back. DATABASE_URL is injected for you.

$ boxx env show <app>
$ boxx env push <app> --file .env  # review, save, redeploy
$ boxx env rollback <app>

doctor and logs

boxx doctor checks the host: Docker, ports 80 and 443, your editor, the state directory and duplicate hostnames.

$ boxx doctor
$ boxx logs <app>
$ boxx ls

boxx is a personal project. It works, and I run my own production sites on it, but it's built for how I work, not as a supported product.

It isn't meant for critical production apps. If you use it, you're on your own: read the code, test it on your setup and keep backups.
